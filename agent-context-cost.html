An agent that takes twelve turns is not twelve calls. At twelve turns the real bill is already several times the estimate, and the last turn alone can cost nine times the first. The Per-Call Estimate Is the Wrong Unit

Almost every agent budget starts the same way: take the average tokens in one request, multiply by the number of requests, multiply by the price. That arithmetic is correct for a stateless service and wrong for an agent, and the error is not a rounding difference. It is structural.

A stateless endpoint sends the same short prompt every time. An agent cannot, because the model has no memory between calls. Everything it needs to know about what happened in turn three has to be re-sent in turn four: the user's instruction, its own previous reasoning, and every tool result it has collected. Context is not a cache the provider keeps for you — it is a payload you re-upload on every call, and you are billed for the upload.

The consequence is that the per-call unit understates the bill by a factor that grows with the loop length. Short loops hide it. A three-turn chain is close to the estimate and looks fine in testing. A twenty-turn research agent is off by an order of magnitude, and nobody notices until the invoice arrives, because the individual calls each looked cheap.

Why the Growth Is Quadratic

Let k be everything one turn adds to the conversation — user message, assistant output, and tool result. The input at turn t is the base plus k for each completed turn before it:

k = user + output + tool tokens added per turn ctx(t) = base + (t - 1) × k input tokens at turn t total_in = N × base + k × N × (N - 1) / 2 sum over all turns est = N × base flat-call estimate overhead = 1 + k × (N - 1) / (2 × base) total_in / est N_2x = 1 + 2 × base / k first turn at 2x overhead

The estimate term is deliberately the flat one: N calls of the same size as the first. That is what a budget written before the loop was instrumented actually contains, and it makes the comparison a like-for-like one rather than a comparison against a per-turn average that already knows the answer. The second term is the whole story. It has an N squared in it, divided by two, and it is multiplied by k — so the marginal cost of adding one more turn is not constant, it is the current context length. Turn twelve is expensive because turns one through eleven are still in the payload.

The N_2x line is the one worth memorising. It says where your estimate stops being usable, and it depends only on the ratio of base to growth. A large system prompt buys you more turns before the error becomes visible, which is a genuinely underrated argument for thorough tool definitions. A small prompt with chatty tool results crosses the threshold almost immediately.

The Last Turn Is the Expensive One

Because context length is linear in the turn index, the cost of a turn is linear in the turn index too. The ratio between the final turn and the first is simply the final context divided by the base. In a loop with a 2,000 token base and 1,500 tokens of growth, the twelfth turn sends 18,500 tokens against the first turn's 2,000 — a factor of 9.25.

This changes what optimisation should target. Averaged over the loop, every turn looks roughly similar and no single turn looks alarming, which is why per-turn dashboards rarely surface the problem. Sorted by cost, the last few turns carry most of the bill. If the loop can terminate earlier — a better tool, a tighter success condition, a cheaper verification step — the saving is concentrated exactly where the money is.

Tool Output Is the Usual Villain

Of the three things a turn adds, tool results are typically the largest and the least examined. A user message is short by design. An assistant answer is bounded by the model's verbosity. A tool result is bounded by whatever the tool returns, which is often raw: a full JSON document, a web page's text, an unfiltered SQL result, a directory listing.

The cost of a tool result is not its length, it is its length multiplied by the number of turns that follow. A 4,000-token result fetched on turn two of a twelve-turn loop is billed eleven times — 44,000 input tokens for one lookup. Trimming that result to 800 tokens before it enters the conversation removes 35,200 tokens from the task, which at $2 per million is seven cents per task and $420 a month at 200 tasks a day.

This is why "return a summary, not a dump" is the highest-leverage change in most agent codebases, and why it is invisible in any per-call analysis. The trimming happens inside the tool, so the model never sees the difference, the quality does not change, and the bill moves by a third.

Compaction Is a Threshold, Not a Strategy

Capping the context at a fixed length converts the quadratic term into a linear one: once the conversation hits the cap, each turn sends the cap instead of the ever-growing history. The saving is exactly the growth that would have happened above the threshold, which is why it rises with turn count and does nothing for short loops.

The threshold itself is the interesting decision, and it has two costs rather than one. Below the cap, the model sees everything and quality is unaffected. Above it, something has to be dropped or summarised, and the summarisation call is itself a completion you pay for. A cap set aggressively saves input tokens and spends them back on summarising, plus whatever quality loss comes from the model forgetting the middle of the task.

Set the cap as input to see the trade in tokens. The default of zero means no compaction, which is what most frameworks do unless you configure otherwise — so if the cap saving field reads as a dash, you are paying the full quadratic price and probably did not choose to.

Two Levers This Page Does Not Price

The first is caching, and it interacts with everything above. The stable part of an agent's context — system prompt, tool definitions, standing instructions — is the same on every turn, which makes it the ideal cache prefix. It is also usually the part that does not grow, so caching it caps the floor of the bill without touching the growth. Whether that trade pays depends on request spacing, which is a separate calculation on the prompt cache break-even page.

The second is model routing. Running early turns on a cheap model and escalating only when the task proves hard is attractive, but it does not change the shape of the curve — it changes the price of the vertical axis. A quadratic bill discounted by 70% is still quadratic, and it still overtakes the linear estimate at the same turn count. Routing buys headroom; it does not buy structure.

What actually buys structure is fewer turns and smaller tool results, in that order. Both are engineering decisions, both are measurable per task, and neither requires a vendor change.

Modelling assumptions

  • Uniform turns. Every turn is assumed to add the same k tokens. Real loops vary — a turn that fetches a large document costs far more than one that answers from memory — and the total is the sum of the actual values, so a uniform mean is an approximation. It is accurate for the average and understates variance.
  • Full history resend. No framework-side trimming, sliding windows, or provider-side conversation state is assumed unless you set a cap. This is the default behaviour of most agent loops and the pessimistic case.
  • Compaction is a hard cap. Setting a cap truncates context to that length rather than summarising it, so the cost of the summarisation call itself is not counted. That makes the cap saving an upper bound.
  • Tool results are billed as input. Results returned inside the conversation are input tokens on the following turn. Tools that bill separately for their own execution are out of scope.
  • Excluded. Prompt caching, batch discounts, reasoning tokens inside a turn, retries, failed tasks, streaming overhead, and any charge for tool execution itself.
  • Month length. Billed days is an input, defaulting to 30. Calendar months range from 28 to 31, a ±10% swing on any monthly figure.
